# Odwołania2JSON — разбор задачи и варианты решения (RU)

> Для команды: Полина, Сева, Артём, Лёша · 21.11.2026 · Польская версия: [WARIANTY_PL.md](WARIANTY_PL.md)

## TL;DR

- **Обучение — синтетика, тест — реальные дела.** 60 синтетических дел (180 PDF с текстовым слоем) против скрытого набора из ≥10 *реальных* дел. Единственный реальный пример в репозитории организаторов — **скан без текстового слоя, с чёрными плашками анонимизации**. Значит: OCR обязателен, а regex «под генератор» на реальных документах развалится.
- **Этап 1 (отбор топ-3 в финал) = 100% F1.** Финал = 50% F1 + 50% расширяемость (новые классы документов только через конфиг, без изменения кода) + прозрачность.
- **Рекомендация — вариант C, «гибрид с конфигурацией»:** правила/regex для идентификаторов + open-source LLM для семантики + проверка «значение реально есть в тексте» + нормализация. Каждый класс документа — один YAML-файл. Для каждого поля сохраняем источник (страница, фрагмент, метод, уверенность). Без LLM решение тоже работает (откатывается на правила) — это страховка на случай, если у жюри не будет нашего API.

## 1. Что мы выяснили (факты из PDF задачи и репозитория UZP)

### Вход / выход
- `input/<дело>/*.pdf` → `output/<дело>/<то же имя>.json`, дерево папок зеркальное.
- **Имя файла не гарантирует тип**: в шаблоне лежат «przyklad odwolanie.pdf» и «negatywny przyklad.pdf». Классифицируем по содержимому.
- 3 класса: `odwolanie`, `pelnomocnictwo`, `przelew` (подтверждение перевода). В одном деле может быть несколько pełnomocnictw.
- **Негативные документы**: в шаблоне есть объявление TED, и JSON для него *не создаётся*. Нужен «отказ» (класс «другое»).

### Формальные требования (README репозитория UZP)
- Python **3.13+**, `requirements.txt`, запуск через CLI или `start.bat`, папки `input` и `output` в корне.
- **Только open source**, включая LLM (open-weights). Запуск on-premise **без GPU**, LLM — через API.
- Бонусы: новые классы документов **только через конфиги**; **прозрачность** экстракции.
- Для выплаты приза нужны: код, инструкция запуска, **Docker Compose**, документация (архитектура, как настраивается экстракция класса, как добавить новый класс).

### Оценка
- Этап 1: F1 на скрытом наборе (≥10 реальных дел) — 100% оценки.
- Финал (до 3 команд): 50% F1 + 50% гибкость/расширяемость. В PDF с описанием задачи веса другие: 50 / 30 / 20 (F1 / гибкость / архитектура и качество).

### Данные
- 60 дел × (`odwolanie.pdf`, `pelnomocnictwo.pdf`, `potwierdzenie_przelewu.pdf`) + эталонные JSON. Генератор — «LAPFormalDoc».
- Синтетика **нарочно разнообразна**:
  - больше 20 вариантов шапки «банка» в przelew и десятки вариантов меток («Rachunek odbiorcy / beneficjenta / uznawany», «Nr ref. / Numer referencyjny / Identyfikator operacji»…);
  - заголовки вразрядку («P E Ł N O M O C N I C T W O»), блоки в разном порядке;
  - консорциумы (6 дел), 2 заказчика (3 дела), mocodawca-физлицо (4 дела);
  - отвлекающая сущность «Wykonawca wybrany»;
  - даты словами («3 lipca 2026 roku»), TED в виде «2026/S 241-999983», который нужно привести к «999983-2026».
- Odwołanie: 2–11 страниц, в среднем ≈11 700 символов (~4 тыс. токенов), максимум ≈30 тыс. символов. В контекст LLM помещается.

### Неочевидные поля (regex их почти не решает)
- `czynnosc_powod_id` (1–12) + канонический `czynnosc_opis` определяются **только по первому zarzutowi**. В данных встречаются только 1–11. **Что такое 12 — спросить менторов.**
- `czynnosc_dzien` — дата обжалуемой czynności из первого zarzutu.
- При консорциуме в `Odwolujacy` попадает только лидер. `prowadzacy_postepowanie`: null, если заказчик один, иначе 1 или 0.
- Имена pełnomocników нужны в именительном падеже (mianownik). В реальных документах будут склонения: «przez radcę prawnego Jana Kowalskiego» → «Jan Kowalski».
- Нормализация: даты в ISO, BZP без пробелов (`2026/BZP00999263`), счета — только 26 цифр, сумма — число.

### Подводные камни
- **Контрольные суммы в синтетике часто невалидны**: NIP валиден в 115 из 189 случаев, REGON — в 85 из 123, IBAN — в 43 из 120. Отбрасывать значения по контрольной сумме нельзя, это только мягкий сигнал. Для реальных сканов он полезен: помогает исправлять ошибки OCR.
- **F1 по полям**: неверное значение даёт FP + FN, а null — только FN. Поэтому при неуверенности выгоднее вернуть null. Галлюцинации LLM напрямую бьют по точности.
- **OCR**: мы проверили RapidOCR (ставится через pip). Скан он читает, но теряет польскую диакритику («Odwolujacy», «Spóka»), а для точного совпадения названий это плохо. Поэтому основной движок — **Tesseract с моделью `pol`**, плюс исправление ошибок LLM-ом; RapidOCR остаётся запасным.
- Междокументная проверка (NIP в odwołaniu = NIP в pełnomocnictwie) годится только для **проверки**, не для заполнения. В эталоне каждого JSON только то, что есть в *этом* документе.

## 2. Варианты

### Вариант A — «Правила» (OCR + regex/якоря + словари, без LLM)
**Как работает:** текст → классификация по ключевым словам → для каждого поля regex или «метка → значение» из конфига → нормализация.
- ✅ Детерминированно, быстро, без внешних API, полностью прозрачно.
- ❌ Хрупко на реальных документах: другие макеты, склонения, ошибки OCR.
- ❌ `czynnosc_powod_id`, `czynnosc_dzien`, выбор лидера, падежи имён regex'ами почти не решаются.
- ❌ Новый класс = писать regex. Это не «только конфиг» для бизнес-пользователя.
- **Качество:** высокое на синтетике, среднее или низкое на реальных. **Риск для этапа 1: высокий.**

### Вариант B — «LLM-first» (OCR → текст → open-source LLM с JSON-схемой)
**Как работает:** текст с номерами страниц + описания полей из YAML → LLM возвращает JSON по схеме → валидация Pydantic → нормализация.
- ✅ Устойчив к разным макетам, понимает семантику и польскую морфологию.
- ✅ Новый класс = YAML с описаниями полей, идеально под критерий «без изменения кода». MVP делается быстро.
- ❌ Галлюцинации, особенно в цифрах NIP/KRS/IBAN у небольших моделей. Недетерминированность.
- ❌ Полная зависимость от API и модели. Если у жюри не будет LLM-endpointа, F1 ≈ 0.
- ❌ Без дополнительной работы прозрачность слабая.
- **Качество:** хорошее, но потолок задают ошибки модели. **Риск: средний** (зависимость от API).

### Вариант C — «Гибрид с конфигурацией» ⭐ рекомендуем
**Как работает:** тот же конвейер, но у каждого поля несколько кандидатов:
1. **правила** — regex и метки для NIP, KRS, REGON, PESEL, IBAN, дат, сумм, BZP, TED;
2. **LLM** — семантика: роли, лидер, czynność, падежи, названия;
3. **проверка** — значение должно найтись в тексте (fuzzy), контрольные суммы как мягкий сигнал, согласованность между документами дела;
4. **уверенность ниже порога → null**, бережём точность.

В трассировку по каждому полю пишем страницу, фрагмент, bbox, метод и уверенность; в UI источник подсвечивается.
- ✅ Лучшее ожидаемое F1: точность дают правила и проверка, полноту — LLM.
- ✅ Прозрачность и расширяемость через YAML.
- ✅ Работает и без LLM (режим `rules`) — страховка.
- ✅ Естественно делится на 4 параллельных потока.
- ❌ Больше кода и координации. Интерфейсы между модулями нужно зафиксировать (в скелете это уже сделано).
- **Качество:** максимальное. **Риск: низкий–средний.**

### Дополнение D — VLM (визуальная LLM) для тяжёлых сканов
Open-weights vision-модель (например, Qwen2.5-VL или Qwen3-VL) по API читает картинку страницы и возвращает текст или сразу JSON. В варианте C подключается как ещё один OCR-движок (`ocr_engine: vlm`) — если найдём API и останется время.

### Сравнение

| Критерий | A · Правила | B · LLM-first | C · Гибрид ⭐ |
|---|---|---|---|
| F1 на синтетике | ★★★★ | ★★★★ | ★★★★★ |
| F1 на реальных документах и сканах | ★★ | ★★★★ | ★★★★★ |
| Расширяемость через конфиг (финал) | ★★ | ★★★★★ | ★★★★★ |
| Прозрачность | ★★★★★ | ★★ | ★★★★★ |
| Независимость от LLM-API | ★★★★★ | ★ | ★★★★ |
| Скорость получения MVP | ★★★ | ★★★★★ | ★★★ |
| Сложность / координация | низкая | низкая | средняя |

## 3. Рекомендуемая архитектура (C)

```
input/<дело>/*.pdf
   │
   ▼
[1] INGEST       pdfplumber: текстовый слой (+ слова с координатами)
   │             страница без текста? → OCR: Tesseract (pol) | RapidOCR | VLM
   ▼
[2] CLASSIFY     сигналы из YAML (regex + веса) → score по каждому классу
   │             неуверенно → LLM zero-shot по описаниям классов
   │             ниже порога → «другое» → JSON не пишем
   ▼
[3] EXTRACT      по YAML класса:
   │               ├─ rules: метки-якоря, regex (NIP/KRS/REGON/PESEL/IBAN/даты/суммы/BZP/TED)
   │               └─ llm:   JSON Schema из YAML + описания полей + инструкции + few-shot
   ▼
[4] MERGE        выбор кандидата · проверка «есть в тексте» · контрольные суммы (мягко)
   │             уверенность < порога → null
   ▼
[5] NORMALIZE    ISO-даты, суммы, только цифры, форматы BZP/TED, словари (czynnosc_powod)
   ▼
output/<дело>/<имя>.json        ← для оценки
traces/<дело>/<имя>.trace.json  ← откуда взято каждое поле (страница, фрагмент, метод, уверенность)
   ▼
Web UI: загрузка PDF → тип + JSON + подсветка источников на странице
```

### Класс документа = один YAML (то, что даёт очки в финале)

```yaml
# config/doc_types/przelew.yaml (сокращено)
id: przelew
name: Potwierdzenie przelewu
classification:
  min_score: 4
  signals:
    - { pattern: 'potwierdzenie (wykonania |realizacji )?(polecenia )?przelewu', weight: 4, scope: head }
    - { pattern: 'rachunek (odbiorcy|beneficjenta|uznawany)', weight: 2 }
output:
  przelew_bankowy:
    type: object
    properties:
      kwota:
        type: number
        description: Kwota przelewu jako liczba (np. 15000.00).
        labels: [Kwota, Kwota operacji, Kwota przelewu]
        normalize: [amount_pl]
      na_rachunek:
        type: string
        description: Rachunek odbiorcy — same cyfry (26), bez „PL” i spacji.
        labels: [Rachunek odbiorcy, Rachunek beneficjenta, Rachunek uznawany]
        normalize: [digits_only]
        validate: [iban_pl]
```

Новый класс = новый файл в `config/doc_types/`. **Демо для презентации:** превращаем «негативный пример» (объявление TED) в новый класс прямо на сцене за 5 минут.

## 4. Стек (общий для всех вариантов; отличается только набор экстракторов)

| Слой | Выбор | Почему / лицензия |
|---|---|---|
| Язык | Python 3.13 | требование организаторов |
| PDF → текст | pdfplumber (+ pypdfium2 для рендера страниц) | MIT / Apache-2.0; слова с координатами для подсветки |
| OCR | Tesseract 5 + `pol` (через pytesseract); запасной — RapidOCR | Apache-2.0; RapidOCR ставится без системных пакетов |
| LLM | любой OpenAI-совместимый endpoint с open-weights моделью: Qwen3, gpt-oss, Bielik, PLLuM, Mistral Small | open-weights (Apache-2.0); локально — Ollama, llama.cpp или vLLM |
| LLM-клиент | `openai` SDK (только как клиент) | Apache-2.0; работает с любым совместимым сервером |
| Схемы и валидация | Pydantic v2 + PyYAML | конфиги классов → JSON Schema → валидация |
| Fuzzy-сопоставление | rapidfuzz | проверка «значение есть в тексте», метрика |
| CLI | Typer + Rich | `start.sh` / `start.bat` |
| API и UI | FastAPI + статический фронт (HTML + Tailwind CDN + Alpine.js + PDF.js) | без Node и сборки; удобно для веб-LLM |
| Поставка | Docker + docker-compose (app, web, опционально ollama) | требование для приза |
| Качество | pytest, ruff, собственный скрипт F1 | метрика с первого часа |

Все зависимости под разрешительными лицензиями (MIT, BSD, Apache-2.0). Для пилота в UZP это плюс.

**Какую LLM брать на хакатоне.** Сначала спросить менторов (см. §8): может, организаторы дадут API к PLLuM или Bielik. Иначе — бесплатные API open-weights моделей (Groq, Cerebras, OpenRouter; актуальность проверить на месте) или локальная Ollama (Qwen3 8B/14B). Код от провайдера не зависит: меняем только `.env`.

## 6. Как работаем

- **Метрика с первого часа:** `python -m evaluation.run_eval` прогоняет 60 дел и считает F1 по полям. Перед каждым PR — прогон, в описании PR указываем F1 до и после.
- **Для тех, кто работает с веб-LLM:** каждый модуль — маленький файл с докстрингом и тестами-спецификацией. Копируете файл, тесты и нужный YAML в чат → получаете реализацию → `pytest` → PR.
- **Git:** ветки `feat/<имя>-<модуль>`, PR в `master`, без force-push. Маленькие частые PR.
- **Сканы:** `scripts/make_scans.py` рендерит синтетические PDF в картинки с шумом, так мы меряем OCR-ветку до появления реальных данных.

## 7. План по фазам (~24 ч; уточнить точный дедлайн)

| Фаза | Время | Что |
|---|---|---|
| 0 | первые 1–1,5 ч | выбор варианта; окружение у всех (`setup.sh` / `setup.bat`); данные (`scripts/fetch_data.py`); вопросы менторам |
| 1 | до ~6 ч | MVP end-to-end на текстовых PDF: классификация + базовая экстракция → первые цифры F1 |
| 2 | до ~14 ч | LLM + проверка + нормализация; OCR-ветка + синтетические сканы; итерации по ошибкам |
| 3 | до ~20 ч | UI с подсветкой источников, Docker, документация (архитектура, «как добавить класс»), отчёт о качестве |
| 4 | последние 3–4 ч | фриз кода, финальный прогон, README, презентация, репетиция демо |

## 8. Вопросы к менторам (задать в первый час!)

1. **Как считается F1?** Точное совпадение или нормализация/fuzzy (регистр, пробелы, кавычки)? Учитываются ли поля, где эталон null? Сравниваются ли списки по порядку?
2. **Как жюри запустит решение?** У себя? Какой LLM-endpoint будет доступен (дадут ли PLLuM или Bielik)? Можно ли указать свой API?
3. Будут ли в тесте **сканы и анонимизированные документы**? Если данные закрыты плашкой, в эталоне null?
4. **Негативные документы**: не создавать JSON вообще (как в шаблоне) или нужен пустой/другой файл?
5. Что означает **`czynnosc_powod_id = 12`**?
6. Может ли **один PDF содержать несколько документов** (odwołanie + приложения одним файлом)?
7. Имена файлов в тесте произвольные?
8. Есть ли ограничение на время обработки?
